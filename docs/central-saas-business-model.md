# POI Hub 中心化 SaaS 收费与资金方案

## 结论

正式商业形态是“一套中央平台服务多个商户”，不再向每家商户安装本地节点。API、微信授权、回调入口、任务队列、数据库、计费、审计和商户启停全部运行在软件方控制的服务器；商户只通过浏览器登录自己的租户空间。

微信小店本地生活和微信服务 POI 是两组相互关联但标识、权限不同的能力：消费者在微信小店购买本地生活券，腾讯地图点位用于创建微信服务 POI，本系统在中央数据库中维护商户、标准门店、腾讯地图点位、微信 POI、本地生活商品与核销门店的显式映射。

官方能力边界参考：[本地生活接入指南](https://developers.weixin.qq.com/doc/channels/dev_before/locallife/guide.html)、[本地生活 API](https://developers.weixin.qq.com/doc/channels/api/locallife/)、[新增本地生活商品](https://developers.weixin.qq.com/doc/channels/api/locallife/shop/api_addlocalproduct.html)、[核销券码](https://developers.weixin.qq.com/doc/channels/api/locallife/useing/api_consumevoucher.html)、[微信服务 POI](https://developers.weixin.qq.com/doc/service/guide/product/WeChat_Store.html)和 [POI 搜索](https://developers.weixin.qq.com/doc/service/api/stores/miniapp/api_poilistsearch)。

## 三条资金线必须分开

| 资金线 | 付款方与收款方 | 系统职责 | 禁止做法 |
|---|---|---|---|
| 消费者货款 | 消费者通过微信小店付款，按微信规则结算给商户 | 同步商品、订单、券、核销、售后和官方账单 | 本系统重复创建一笔消费者订单或代持消费者资金 |
| 微信平台费用 | 微信账单中的佣金、结算金额等官方字段 | 原样入账并与关联订单核对 | 把 `commission_fee` 直接记成软件服务费收入 |
| POI Hub 服务费 | 商户按与软件方签订的 SaaS 合同付款给软件方 | 订阅、用量、账单、收款、欠费和启停 | 未获得明确能力和授权就从消费者货款自动截费 |

因此，“支付收取”分为两件事：消费者付款继续完全走微信小店；软件方收商户服务费要建立独立的 B2B 收款闭环。早期可以使用对公转账或独立收款单并由总部核销，具备相应支付商户资质和协议后再接自动支付/代扣。支付渠道只负责收款，平台自己的订阅和账单台账才是应收事实源。

## 推荐收费产品

### 第一阶段：固定订阅 + 超量月结

- 基础订阅按月或按年，包含商户账号、门店数、微信连接数和基础操作量。
- 超出套餐的成功核销量按阶梯单价计费；撤销核销和退款生成冲正，不直接删除原记录。
- 初始实施、地图点位整理、商品迁移可作为一次性实施费。
- 账单以整数分计算，保存费率版本、用量来源、账期和计算快照，历史账单不随新价格回算。
- 逾期先提醒和进入宽限期；宽限期结束由总部停用租户。停用只阻止业务访问，不删除数据，付款后可恢复。

这种模式比从每笔消费者支付中抽成更容易解释、开票、退款和对账，也不依赖未经确认的微信分账能力。

### 第二阶段：自动收款

自动收款必须建立在软件方真实签约并获准使用的支付产品之上。推荐流程是：

1. 平台账单结算后创建一笔不可重复的服务费收款单。
2. 支付渠道返回支付单号；异步通知只更新收款状态，不直接改写用量。
3. 验签、金额、商户、币种和幂等校验全部通过后，将收款核销到指定账单。
4. 少付、重复付、退款和拒付分别形成调整记录，不覆盖历史支付。
5. 支付成功恢复欠费商户；失败进入重试与人工处理，不对消费者订单做任何操作。

## 中央架构

~~~text
商户浏览器 ──HTTPS──> WAF / 负载均衡 ──> API 实例（2+）
微信授权与回调 ──────> 统一公网回调入口 ──> 加密收件箱
                                              │
                           PostgreSQL 主库 <──┼──> Worker 集群 ──HTTPS──> 微信官方 API
                                  │           │
                                  ├── 订阅/用量/账单/支付
                                  ├── 租户与权限/审计
                                  └── 备份、只读副本、监控
~~~

- 所有业务表必须带 `tenant_id`，所有接口按当前租户过滤；平台管理员拥有跨租户主控能力。
- 每个商户的微信凭据、回调整包、券码和敏感任务参数分别加密保存，界面只显示脱敏摘要。
- 总部可以停用或恢复商户。停用后的现有登录会话也不能继续访问该租户。
- 正式环境强制 PostgreSQL；SQLite 只用于开发，不存在“每客户一个本地数据库”。
- API 无状态横向扩容，Worker 使用数据库租约并可横向增加。Redis 可在规模扩大后承担全局限流、短期缓存和 component token 单飞，但不能取代持久账本。
- 回调域名、证书和出口 IP 都由软件方统一维护，商户不需要公网服务器。

## 微信授权批量化

批量商用推荐由中央平台完成商户授权：

1. 商户在平台发起微信授权，授权结果绑定到一个且仅一个租户。
2. 中央服务维护 component ticket、component access token、预授权码、authorizer refresh token 和权限快照。
3. token 只在服务端解密和刷新，不传给浏览器；同一授权方刷新使用分布式单飞锁。
4. 回调先按 AppID/授权方路由，再验签、AES 解密、去重和落入加密收件箱。
5. 取消授权、权限减少或 token 失效立即将连接标记为异常，并停止对应自动任务。

当前代码已具备 authorizer refresh token 的使用、连接密钥加密和中央回调处理；第三方平台 component ticket/token 的持续刷新和完整授权门户仍是正式售卖前的 P0，不应通过手工复制长期密钥来批量开户。

## 服务费台账的最低数据模型

正式收费前至少补齐以下不可变账务对象：

- `plans`：套餐版本、包含额度、计费项和有效期。
- `subscriptions`：租户当前套餐、账期、宽限期、续费和停用策略。
- `usage_events`：成功核销等原始计费事件，使用业务幂等键防重复。
- `invoices` / `invoice_items`：应收账单及逐项计算快照。
- `payments`：渠道单号、实收金额、状态、通知指纹和核销关系。
- `adjustments`：撤销、退款、减免、补收和坏账，不删除原账。

现有 `Tenant.status` 总闸已经可用于总部停用/恢复，但它不是完整订阅台账；在上述模型上线前，只能做人工签约、人工账单和人工收款核销试点。

## 商业上线门槛

1. 完成微信第三方平台授权门户和 component token 生命周期。
2. 建立服务费订阅、用量、账单、支付和冲正台账。
3. 部署双 API、多 Worker、PostgreSQL 备份与恢复演练、集中监控和告警。
4. 做 10 万级混合任务、回调乱序、微信 429/5xx、Worker 强杀和数据库故障演练。
5. 完成隐私政策、数据处理协议、账务口径、退款政策、开票和欠费停服条款。
