# POI Hub 中心化商业与批量化对抗性审查

审查日期：2026-08-24
结论：**当前代码可进入少量商户、人工收费的受控 SaaS 试点，但不能宣称已具备自动服务费收取或大规模正式商用能力。**

## 1. 商业边界判断

消费者交易属于微信小店本地生活：微信承载消费者付款、订单、券和商家结算。POI Hub 是商户侧中央运营 SaaS，负责微信授权、腾讯地图/微信服务 POI、商品、券码、核销、售后、官方账单核对以及另行向商户收取软件服务费。

最危险的商业误区有两个：一是把微信账单字段 `commission_fee` 当成软件收入；二是在没有明确官方能力、支付资质和合同授权时，声称可从消费者货款中自动抽成。正确做法是把消费者货款、微信侧费用和 POI Hub 服务费建成三套相互关联但独立的账。

协议实现依据：[本地生活接入指南](https://developers.weixin.qq.com/doc/channels/dev_before/locallife/guide.html)、[本地生活 API](https://developers.weixin.qq.com/doc/channels/api/locallife/)、[新增本地生活商品](https://developers.weixin.qq.com/doc/channels/api/locallife/shop/api_addlocalproduct.html)、[核销券码](https://developers.weixin.qq.com/doc/channels/api/locallife/useing/api_consumevoucher.html)、[微信服务 POI](https://developers.weixin.qq.com/doc/service/guide/product/WeChat_Store.html)和 [POI 搜索](https://developers.weixin.qq.com/doc/service/api/stores/miniapp/api_poilistsearch)。

## 2. 已完成的关键加固

| 攻击或故障 | 原始风险 | 当前控制 |
|---|---|---|
| 越权访问其他商户 | 仅依赖前端选择租户会造成数据串租 | 后端租户作用域、固定 RBAC、平台管理员单独授权；停用租户立即拒绝访问 |
| 总部失去商业控制 | 商户端独立部署无法统一停服和升级 | 默认中心 SaaS；新增总部商户总闸，可停用/恢复且保留数据 |
| 出站 SSRF | 商户连接字段诱导 Worker 访问内网或云元数据 | 出站主机由平台配置；生产只允许微信官方 HTTPS 主机 |
| 回调伪造或重放 | 伪造发券/订单事件、重复核销 | 签名、AES 解密、AppID 校验、大小限制、指纹去重、加密收件箱 |
| 券码与隐私泄露 | 券码、openid、联系电话进入数据库明文字段或日志 | 券码指纹、AES-GCM 密文、展示脱敏；完整任务和回调整包加密 |
| 队列毒消息 | 首条失败事件无限占据队首 | 租约、指数退避、最大次数、死信、人工批量重放 |
| Worker 崩溃或重复执行 | 租约到期、实例重名和网络超时产生重复副作用 | 唯一 Worker ID、所有权校验、续租、稳定幂等键、状态反查 |
| 批量连接风暴 | 每次调用创建新 TCP/TLS 连接 | API/Worker 生命周期共享有界 HTTP 连接池 |
| SQLite 锁死生产 | 多 API/Worker 并发写单机库 | 中央生产现在强制 PostgreSQL；SQLite 仅用于开发 |
| 微信协议错位 | 错误商品字段、券查询条件、核销参数和 POI 单阶段创建 | 已按官方契约重写并加入契约测试 |
| 假对账 | 把无关联的资金与券账单总额直接相减 | 只按关联订单比较，并单独报告未关联记录 |

## 3. 阻止正式大规模售卖的 P0

### 3.1 微信第三方平台授权闭环未完成

当前可使用 authorizer refresh token 刷新商户令牌，但还缺中央 component ticket/token 持续刷新、预授权码、商户授权门户、取消授权处理和权限缩减告警。没有这一层，批量开户仍依赖人工复制密钥，既不安全也无法规模化。

### 3.2 软件服务费账本未完成

总部停用/恢复只是执行总闸，不是计费系统。正式收费需要套餐版本、租户订阅、不可变用量事件、整数分计价、账单明细、支付核销、撤销/退款冲正、宽限期和开票状态。任何支付渠道的成功通知都只能核销平台账单，不能替代应收账本。

### 3.3 高可用与灾难恢复未达到资金系统标准

正式环境至少需要两台 API、多个 Worker、受管 PostgreSQL、自动备份与恢复演练。数据库、回调入口或 DNS 单点故障都会导致券码延迟入库和核销不可用。需要明确 RPO/RTO、跨可用区策略、数据库连接池上限和降级方案。

### 3.4 运营可观测性不足

readiness 不能只检查数据库。至少应监控：队列深度、最老任务年龄、任务成功/重试/死信率、回调积压、微信延迟与 429、token 刷新失败、数据库连接与慢查询、账单生成失败、支付通知验签失败、租户停用动作和 Worker 最后心跳。

## 4. 扩容前的 P1

1. 商品、订单、门店、成员、券和流水列表统一改为稳定游标分页，避免百万级数组拖垮 API 与浏览器。
2. 为 component token、商户 token 和微信配额建立跨实例单飞锁与租户级/能力级限流；Redis 建议用于协调，不作为财务账本。
3. 所有外部写操作继续按“至少一次”设计：稳定业务请求号、结果查询、对账和人工补偿必须同时存在。
4. 计费用量只能来自已确认的业务事实，例如成功核销；撤销核销必须生成反向事件，禁止直接修改或删除原用量。
5. 对批量任务设置租户配额和公平调度，避免一个大商户占满所有 Worker 与微信调用额度。

## 5. 企业与合规阶段的 P2

- 平台管理员强制 MFA，高风险停用、密钥变更和支付退款增加二次确认与双人审批。
- 使用 KMS/HSM 管理主密钥，支持密钥版本、轮换、重加密和权限审计。
- 审计日志增加防篡改链、异地归档和 SIEM 投递；请求 ID、操作 ID、微信请求号、账单号和支付单号全链路关联。
- 补齐服务账号/API Key 生命周期、开放 API 版本政策、租户导出、注销、删除证明和隐私请求流程。
- 明确数据驻留、日志保留、备份加密、子处理方、客服访问和事故通知制度。

## 6. 容量和故障演练

建议从 PostgreSQL、2 个 API 实例、2～4 个 Worker 起步，根据微信接口配额和实际延迟扩容。`WORKER_CONCURRENCY` 不是越大越好，必须同时受数据库连接池和上游限流约束。

上线前至少验证：

1. 10 万条多租户混合操作，持续注入 1% 超时、429 和 0.1% 永久失败。
2. 同一商户重复回调、跨商户伪造 AppID、回调乱序和 1 MB 边界载荷。
3. Worker 执行中强杀、租约回收、重复命令与微信响应丢失。
4. 大商户突发任务下，小商户仍能在目标时间内获得处理能力。
5. PostgreSQL 主库切换、连接耗尽、磁盘满、备份恢复和错误迁移演练。
6. 重复支付通知、少付/多付、退款、服务费账单冲正和逾期停用/付款恢复。

## 7. 商业化路线

- **受控试点**：3～5 个商户，固定订阅或人工月结，总部人工核销收款；统一公网回调和 PostgreSQL。
- **计费闭环**：上线订阅、用量、账单、支付与冲正台账，再接独立支付渠道；消费者付款仍由微信小店完成。
- **批量开户**：完成微信第三方平台授权门户、component token 生命周期、取消授权和权限变化处理。
- **规模化 GA**：高可用、容量压测、恢复演练、MFA/KMS、账务审计和合规条款全部达标。

收费与架构细节见 `docs/central-saas-business-model.md`，服务器部署基线见 `docs/deployment.md`。
