## 1. 先给结论

当前项目不是空壳，已经拥有可运行、可测试的 SaaS 后台、微信位置准入流程、单商家小程序交易闭环和小程序页面骨架。现有版本适合做“一个商家登记一个小程序”的受控试点。

当前版本还不能直接宣称已经实现方案二的正式批量运营。方案二要求“一个平台 AppID 服务多个商家”，现有代码仍把小程序登记和消费者身份绑定在商户租户内，并按一个小程序登记选择一个支付连接。正式上线前必须完成平台级小程序、门店入口路由、逐单商户支付路由、退款/关单/查单、服务费账单和生产部署等改造。

| 目标 | 开发与联调时间 | 不包含 |

## 2. 方案二的最终业务链路

```text
腾讯地图/微信位置门店页
        │ 携带 store_code 或 scene
        ▼
平台统一小程序（只有一个平台 AppID）
        │ 解析入口并打开对应门店
        ▼
门店主页 → 套餐 → 下单 → 微信支付 → 预约 → 券码
                      │
                      ├─ 普通商户试点：订单选择该店已绑定的商户号
                      └─ 批量模式：服务商 sp_mchid + 该店 sub_mchid
        ▼
POI Hub SaaS
  总部：全部商家、风控、报备、账单、审计
  商家：只看自己的门店、商品、订单和结算
  店员：只看预约并核销本店券码
```

资金原则：消费者付款不得默认进入软件公司的普通收款账户再人工转给商家。推荐批量路线是微信支付服务商模式，由平台小程序发起交易，订单填写对应门店的 `sub_mchid`，消费者货款进入子商户账户。微信支付官方把服务商模式定义为系统开发商帮助没有开发能力的中小商户完成入驻、开发和运营；该模式使用 `sp_mchid + sub_mchid`。如果服务商资质尚未完成，第一家店只能在微信平台允许的前提下，使用商户自己的普通商户号与平台 AppID 完成绑定后进行直连试点。

平台 SaaS 服务费与消费者货款分开：第一阶段采用合同＋独立收款单＋人工核销；完成计费台账和支付资质后再自动收取。不得把微信佣金字段当成平台服务费，也不得在没有官方分账权限时私自抽取顾客货款。

## 5. 方案二必须完成的技术改造

### P0-1：平台级小程序模型

现状：`MerchantMiniProgram` 带 `tenant_id`，小程序配置固定一个 `miniProgramId`。这天然偏向“每家一个小程序”。

目标：

1. 新建平台级 `platform_mini_programs`，由平台保存唯一 AppID、AppSecret、版本和启用状态。
2. 新建 `mini_program_store_bindings`，保存平台小程序、租户、门店、公开 `store_code`、腾讯地图 POI、入口路径、入口 `scene` 和审核凭证。
3. 同一个平台 AppID 下允许绑定多个租户/门店；门店必须保持租户隔离。
4. 小程序打开 `pages/store/index?store_code=...` 或携带 `scene` 时，服务端解析并返回该门店，而不是从客户端接受任意 `tenant_id`。
5. 未发布、欠费停用、报备未通过或绑定失效的门店必须返回不可交易状态。

验收：用两个测试租户共用同一 AppID，分别从两个入口进入，只能看到各自门店商品；篡改 `store_code` 不能越权读取另一店的非公开数据。

### P0-2：平台级消费者身份

现状：消费者 OpenID 按 `tenant_id + mini_program_id` 保存。统一小程序中 OpenID 属于平台 AppID，不应该因进入不同商家重复创建身份。

目标：

1. 消费者身份改为平台 AppID 维度；保存加密 OpenID、哈希和账号状态。
2. 顾客会话属于平台小程序，不属于某个商户。
3. 订单授权仍校验订单属于当前顾客；商家后台仍受租户过滤。
4. 顾客跨门店订单页可按门店归类，但商户绝不能看到其他商户的顾客订单。

### P0-3：逐门店支付路由

现状：一个小程序登记只绑定一个 `connection_id/payment_merchant_id`。

目标：

1. 新建 `merchant_payment_profiles`，按租户/门店保存支付模式、商户号、授权状态和有效期。
2. 创建订单时把支付模式、`mchid/sub_mchid` 和费率版本快照到订单，后续不能因商户改配置而把旧订单路由到别的收款方。
3. 普通商户试点：校验平台 AppID 与该商户号确有绑定关系。
4. 批量模式：新增微信支付服务商网关，使用 `sp_appid + sp_mchid + sub_mchid`；如果在平台小程序调起支付，OpenID 必须来自平台 `sp_appid`。
5. 支付回调不能再只按 URL 中的小程序登记 ID 找密钥，应先安全验签/解密，再按订单号、`sp_mchid/sub_mchid` 和支付配置快照路由。
6. 禁止前端传入商户号决定收款方；只能由商品所属门店在服务端决定。

官方硬约束：普通模式 `appid` 与 `mchid` 必须绑定；服务商模式用于帮助无开发能力的中小商户，资金进入订单指定的 `sub_mchid`。服务商模式需要真实申请，不是改几个参数就能自行获得。

### P0-4：真实支付完整生命周期

现状已有下单和成功回调，但正式收款还缺：

- 超时主动关单和库存定时释放。
- 回调丢失时主动查单。
- 顾客取消支付和重复调起处理。
- 退款申请、退款回调、退款查询、部分退款和幂等退款单。
- 退款后券码作废、预约取消和库存/已售口径。
- 交易账单下载、逐单对账和差异工单。
- 回调证书/微信支付公钥轮换演练。

微信支付文档明确指出，`time_expire` 到期不等于自动关单；商户仍应调用关单接口。退款、查单、回调和账单也是正式支付链路的一部分，不能只依赖一次成功回调。

### P0-5：修复多数量订单和履约模型

当前订单允许 `quantity > 1`，但 `DirectVoucher.order_id` 是唯一值，支付后只生成一张券。上线前必须选择并固定一种规则：

- 方案 A：第一版强制每单数量只能为 1；或
- 方案 B：按数量生成多张券，并定义部分核销、部分退款和有效期。

试点建议先选 A，降低退款和核销复杂度；数据库和接口要明确拒绝数量大于 1，而不是静默少发券。

### P0-6：平台统一小程序前台

至少补齐：

1. 启动参数与腾讯地图入口解析。
2. 门店头图、名称、地址、营业状态、电话、导航、服务说明。
3. 套餐列表、详情、购买须知、退款规则和长发/漂色补差说明。
4. 登录、订单确认、支付结果、订单列表和详情。
5. 预约日期/时段、联系人、改约/取消规则。
6. 券码/二维码、有效期、门店和核销状态。
7. 客服、隐私政策、用户协议、注销/数据权利入口。
8. 空状态、失败重试、支付取消、商品下架和门店停业提示。

首页应按入口直达单店，不强迫腾讯地图来的顾客再次搜索；平台内自然进入时才展示附近门店或搜索能力。

## 6. 产品和支付路线决策

### 推荐路线

1. 平台主体注册一个统一小程序。
2. 第一家“缔丝风尚”先使用普通商户直连完成真实 0.01～1 元测试，但前提是微信后台允许并完成平台 AppID 与该商户号的绑定。
3. 同时申请微信支付服务商身份；第二批商家优先按特约商户/子商户模式接入。
4. 服务商模式验证完成后，平台只持有服务商侧证书和 APIv3 密钥，订单按门店选择 `sub_mchid`，商户不需要把自己的 API 私钥交给普通运营人员。
5. SaaS 服务费独立开账和收款，不与顾客货款混账。

### 明确禁止的路线

- 用软件公司的普通商户号收取所有商家的顾客货款，再线下转账。
- 由小程序前端传入 `mchid/sub_mchid`。
- 把 AppSecret、API 私钥、APIv3 密钥写入小程序或 GitHub。
- 为了通过审核而填假类目、借用别家营业执照或伪造官方通过截图。
- 未获得腾讯/微信接口权限就宣传“已与腾讯地图原生订单自动同步”。

6. 推送到用户自己的 GitHub remote，并给分支设置 upstream。
7. 从该基线创建统一小程序开发分支。

当前仓库事实：已配置 `origin` 和用户自己的 `user` remote；当前分支没有显示 upstream；大量功能仍是未提交文件。交接人员不得先清理或覆盖工作区，否则可能丢失准入、交易和小程序实现。

阶段验收：干净工作树、远端可见提交、克隆后能够按 README 跑通全部测试。

### 阶段 1：主体与外部账号准备（与开发并行，1～5 天或更长）

负责人：项目负责人＋商户。

平台方准备：

- 平台小程序注册主体、名称、Logo、AppID/AppSecret。
- 小程序备案、服务类目、隐私保护指引、用户协议和客服联系方式。
- 一个正式 HTTPS API 域名，并在小程序后台配置合法域名。
- 微信支付服务商申请材料；未通过前准备单店普通商户试点路线。

缔丝风尚准备：

- 营业执照、经营者身份核验、结算账户。
- 腾讯地图门店已认领且“正常营业”的截图；当前已有这一项。
- 腾讯地图 POI ID、准确经纬度、营业电话、营业时间。
- 6 张合规门店图片，套餐封面和真实服务说明。
- 微信支付商户认证、超级管理员确认和商户号。
- 第一款低风险测试商品，明确价格、有效期、预约、补差和退款规则。

阶段验收：所有编号可从官方后台反查；密钥只通过受控后台/密钥库交付，不经聊天传输。

### 阶段 2：统一小程序核心重构（3～5 天）

负责人：后端＋数据库开发。

1. 设计并评审平台小程序、门店入口绑定、平台消费者、商户支付配置模型。
2. 编写 Alembic 前向迁移，保留当前单商家数据的迁移策略。
3. 改造登录和公开 API，以平台 AppID 登录、以服务端入口解析门店。
4. 改造商品、订单和券，使门店/租户从可信绑定关系得出。
5. 修复数量与券的关系。
6. 添加两个租户共用一个 AppID 的隔离测试、入口篡改测试和错误支付路由测试。

### 阶段 3：支付和售后完善（3～5 天）

负责人：支付后端开发＋财务验收。

1. 保留普通商户网关用于第一店。
2. 新增服务商模式网关和 `sp_mchid/sub_mchid` 配置。
3. 实现主动查单、关单、库存释放、退款和退款通知。
4. 实现日账单下载、逐单对账和差异状态。
5. 用微信沙箱/低金额真实订单验证：成功、取消、超时、重复回调、少付/金额不符、退款和重复退款。

阶段验收：顾客账单显示正确商家/商品；货款进入正确商户；SaaS、微信商户平台和顾客支付记录金额一致。

### 阶段 4：统一小程序成品化（3～5 天）

负责人：小程序前端＋产品/设计。

1. 根据 `store_code/scene` 直达门店。
2. 完成门店、套餐、确认订单、支付结果、订单、预约、券码和我的页面。
3. 加入隐私、协议、客服、错误状态和埋点。
4. 对缔丝风尚做真机全链路测试。
5. 完成体验版、审核版和发布版本号管理。

### 阶段 5：运营后台与服务费（2～4 天）

负责人：全栈开发＋运营＋财务。

1. 把“商家小程序”页面调整为“平台小程序门店接入”。
2. 做一步式开通向导：门店→材料→地图→支付→商品→试单→上线。
3. 加对象存储上传和审核材料查看。
4. 加退款、预约排班、核销和异常工单页面。
5. 完成套餐、订阅、账单、人工收款核销和欠费宽限期。

### 阶段 6：腾讯地图挂载（开发并行，外部时间不受控）

负责人：位置运营人员＋平台管理员。

1. 从腾讯地图商户中心取得正确门店 POI 标识和认领凭证。
2. 申请/配置平台小程序服务入口，路径使用门店专属 `store_code` 或 `scene`。
3. 在 POI Hub 保存申请号、审核结果和完整截图。
4. 用普通顾客微信从地图位置页进入，确认直达正确门店。
5. 验证修改参数不能打开别家后台数据或把订单付给别家商户号。

注意：当前“正常营业”截图证明腾讯地图门店认领成功，不等于平台小程序挂载、微信服务 POI、本地生活类目和支付均已批准。

### 阶段 7：服务器部署和试点（2～3 天）

负责人：运维＋技术负责人。

1. 先盘点现有服务器端口、3x-ui 服务、证书和防火墙，只读确认后再部署。
2. SaaS 使用独立系统用户、目录、数据库、内部端口和子域名。
3. 生产使用 PostgreSQL；只允许 Nginx/Caddy 对外暴露 443，API/数据库使用内网或回环地址。
4. 配置 Secret、加密密钥、微信凭据和回调；不得写入仓库。
5. 单独执行 `alembic upgrade head`，不得在生产运行 seed reset。
6. 创建首个平台管理员，启动 API、Worker 和前端。
7. 做健康、登录、租户隔离、支付回调、退款、核销和审计冒烟测试。
8. 配置备份、证书到期、磁盘、5xx、回调和 Worker 告警。

现有 AkileCloud 服务器为 1 核约 1.5 GB 内存、10 GB 系统盘，并运行 3x-ui。它可用于极小流量的临时试点，但不适合同时承担正式数据库、支付回调、SaaS 和代理业务。正式收费前建议把 SaaS/数据库迁移到独立资源，至少避免与 3x-ui 形成共同故障和安全边界。

3x-ui 保护原则：不改已有入站、节点、监听端口、证书和数据库；不复用其管理域名；上线前后分别截图并检查监听端口与服务状态；出现冲突先停止 SaaS 发布，不通过修改 3x-ui 解决。

## 8. 缔丝风尚第一店详细执行顺序

### A. 现在即可完成

1. 在腾讯地图商户中心补齐 6 张门店图片、营业时间、电话和美发标签。
2. 记录腾讯地图 POI ID/地点 ID；不要只保存截图。
3. 准备一款测试套餐，例如“潮色染发体验”，只允许购买 1 份。
4. 写清楚适用长度、是否含漂色、补差、预约提前时间、不可用日期、有效期和退款条件。
5. 完成商户支付认证并确认真实商户号及超级管理员。

### B. 平台方并行完成

1. 确定平台小程序名称、Logo、主体和客服电话。
2. 注册并取得平台 AppID/AppSecret。
3. 完成备案、隐私和服务类目准备。
4. 确定试点支付路线：普通商户绑定平台 AppID，或已批准的服务商子商户模式。
5. 建立正式 API 子域名和 HTTPS。

### C. 技术联调

1. SaaS 创建缔丝风尚租户和门店。
2. 上传/引用地图认领凭证，预审真实资料。
3. 创建该门店的 `store_code`，配置小程序路径。
4. 配置该店支付档案并由两人复核商户号。
5. 创建 0.01～1 元测试商品，库存 1，数量上限 1。
6. 从体验版进入：登录→下单→支付→预约→出券→店员核销。
7. 测试重复核销、支付取消、超时、退款、入口篡改和错误门店支付拦截。
8. 三方核对顾客账单、微信商户平台和 SaaS 订单。

### D. 地图验收

1. 提交腾讯地图/微信位置服务入口。
2. 审核通过后，从普通顾客微信真实打开。
3. 检查门店名、地址、电话、导航、图片、服务按钮和直达路径。
4. 完成一笔真实低金额订单并退款。
5. 观察 24 小时回调、任务、对账和告警后再正式发布套餐。

## 10. 上线验收清单

只有以下项目全部通过，才能将第一店标记为正式营业：

- [ ] 平台小程序 AppID、主体、备案、类目、隐私和版本审核有效。
- [ ] 腾讯地图门店认领有效，入口直达正确 `store_code`。
- [ ] 缔丝风尚支付商户号已由商户超级管理员确认并完成 AppID 关联。
- [ ] 服务端按门店决定收款账户，客户端无法篡改。
- [ ] 消费者货款进入缔丝风尚账户，不进入平台普通账户。
- [ ] 支付成功、取消、超时、查单、关单和退款通过。
- [ ] 回调验签、解密、AppID、商户号、订单号、金额和幂等校验通过。
- [ ] 单店入口、商品、订单、预约和券码无跨租户泄漏。
- [ ] 券码只能核销一次，退款券不能核销，误核销有审批和审计。
- [ ] 顾客、商户、店员、运营和平台管理员权限分别验证。
- [ ] 服务费有独立合同、账单和收款记录。
- [ ] 数据库备份已完成一次真实恢复验证。
- [ ] 3x-ui 的服务、端口和连接在部署前后均正常。
- [ ] 24 小时观察期内无未处理支付回调、死信和账务差异。
