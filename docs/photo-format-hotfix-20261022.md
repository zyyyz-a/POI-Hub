# 照片与结算账号格式修复（2026-10-22）

## 现象与原因

用户上传门头、店内照片后收到「请上传真实的JPG、PNG或BMP照片」。线上确认对应请求为422，不是原2MB限制；相同申请仍只保存了执照和身份证两面。

旧前端对5MB以内的文件直接原样上传，仅信任文件MIME类型；后台检查实际PNG/BMP/JPEG签名，并要求JPEG具有标准结束字节。错误标记为JPG的WebP、带额外尾部数据的JPEG等，可能被拒绝。没有取得用户失败照片原件，因此不能将某种具体编码断言为该原件的唯一原因；本次已覆盖这些可复现的兼容性缺口。

另经只读格式核对，结算账号中含空格，未发现掩码；没有输出账号数字，也没有更改生产记录。

## 修改范围

- 所有文件先识别真实字节并尝试本地解码；拒绝伪装图片的SVG/PDF/视频、损坏照片和过大分辨率。
- 兼容误标MIME、WebP/AVIF（浏览器支持时）和带尾部数据的JPEG；按需转换标准PNG/JPEG，保留长宽比，不裁剪。原图20MB、处理后5MB上限不变。
- 小图兼容转换优先尝试无损PNG；合规且无需处理的PNG/BMP/JPEG保留内容。超过上限时沿用本地压缩流程。
- 图片旁新增材料说明和就地错误提示。强调使用统一平台小程序，不要求门店另做；门头、店内及服务页面必须真实对应该店。
- 用户输入或手动保存草稿时，仅去除结算账号中的空白字符；不改数字、不去前导零、不修补掩码、不自动保存生产资料。
- 不放宽后端图片校验、资料完整性、经营者授权和真实提交的二次确认。

## 验证

- 浏览器生成三类真实可解码合成图片，分别上传到门头、店内、小程序截图入口：WebP误标JPG、JPEG加尾部数据、PNG误标JPG均成功生成标准PNG，尺寸保持1600×1000。
- 将上述浏览器输出送入隔离SQLite库中的真实API上传和保存接口，六类照片齐全、必填检查通过，申请仍为草稿；所有微信对外请求被拦截。
- 损坏JPEG在浏览器被拒绝，未发送上传；约18.7MB大图处理为约4.4MB，尺寸3000×2000保持不变。
- 账号格式测试覆盖空格、不可断空格、全角空格、前导零、掩码/字母/短横线保留，以及旧草稿仅在点击保存后规范化。
- 浏览器交互验证一次明确的模拟草稿保存，账号数字完全保留，无自动保存或商户提交。
- 最终前端59项测试通过，生产构建、类型及代码规范检查通过；隔离后台整条上传保存流程复测通过。前端测试中的既有Ant Design高度提示、构建的大分包提示为非阻塞警告。

## 发布

先发布照片修复 `hotfix-20261022-photo-format`，随后发布包含账号格式处理的最终版 `hotfix-20261022-photo-format-bank`。仅更新前端，无API重启、数据库迁移或生产商户资料写入。原静态资源保留，真实进件开关不变。

对应回退备份在 `/opt/poi-hub/.deploy-backups/` 下的同名目录。用户刷新后台，重新选择照片，再点「保存草稿」更新旧账号格式及核对缺项；平台不会替用户提交申请。

最终公网HTTPS首页及8个静态资源校验值一致，健康与门店接口正常，门店仍为 `tradable=false`。未登录的3MB及5MB模拟上传均返回正常身份校验401，而非大小限制413；该公网检查不保存照片。生产环境配置校验值未改变，真实进件开关仍保持开启。

官方依据：[特约商户进件说明](https://pay.wechatpay.cn/doc/v3/partner/4012719997)，服务商小程序AppID可用于小程序场景；线下场所材料要求门头、内部照片。小程序截图按场景及建设/上线情况提供，不代表必须给每家店重新开发小程序。
